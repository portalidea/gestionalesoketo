## Cosa non permette di conoscere il vecchio handler

Il report ID ricevuto dal modulo 97 **non è stato salvato**. Il campo `error` è NULL e `summary` è `{}`. Il vecchio handler convertiva qualsiasi eccezione non-Zod nello stesso 409, con log `request_failed`, senza conservare causa, codice, metadati di confronto o correlation ID. I soli DB e log forniti non consentono quindi di attribuire il rifiuto a REPORT_ID_MISMATCH, compressione, struttura del file o errore database.

Lo stato `pending` è ammesso dal motore e la configurazione attuale non risulta disabilitata. Questo esclude quei motivi sulla fotografia attuale, non dimostra retroattivamente quali valori fossero presenti nella richiesta o in tutta la transazione fallita. Non indichiamo un’ipotesi come “motivo esatto”.

Il modulo 97 del blueprint pubblico usa `X-Amazon-Report-Id = {{1.data.report_id}}`, run dal modulo 1, documento e DONE dal modulo 90, compressione dal modulo 93, corpo dal campo Data di 95. Il confronto statico è coerente. Occorre il confronto privato dei valori realmente risolti oppure un nuovo tentativo autorizzato dopo il deploy diagnostico. Nessun payload reale o segreto è stato letto durante questo intervento.

## Correzione locale del server

Il branch **fix/amazon-import-safe-diagnostics** introduce un catalogo chiuso di codici, messaggi italiani sicuri e fasi: authorization, store, metadata, execution, document, database, processing. La risposta e il log hanno lo stesso `errorCode` e un `requestId` casuale; nessun Seller Account ID, store UUID, chiave, URL firmato, body, SQL, messaggio arbitrario o dati cliente viene serializzato.

Tra i controlli distinti: STORE_DISABLED, STORE_SCOPE, REPORT_ID_MISMATCH, RUN_NOT_FOUND, EXECUTION_STATE, DOCUMENT_REPLAY_MISMATCH, REPORT_NOT_DONE, metadati invalidi, compressione non supportata/incoerente, GZIP invalido, codifica, intestazioni, numero/struttura di righe, limiti dimensionali e vincoli DB. La mappatura PostgreSQL conserva solo SQLSTATE ammessi, mai query/detail/error message. Anche il messaggio di un’eccezione tipizzata viene ricostruito dal catalogo anziché riflesso.

`checks` contiene soltanto presenza del report/document ID e, quando verificabili, esistenza del run e uguaglianza delle identità. Non conserva gli identificativi ricevuti. `details` ammette solo nome di una intestazione di schema, numero di riga, quantità di byte, etichette plain/gzip/NONE/GZIP e SQLSTATE. Il parser non espone valori di riga errati.

Dopo il rollback della richiesta, un errore autenticato riferito a un run dello store E-Keto autorizzato viene registrato in **amazon_import_runs.error** e **summary.lastDiagnostic**, usando le colonne della 0051 già applicata. Nessuna nuova migration. L’UPDATE diagnostico non cambia stato, report ID, documento, righe, allocazioni o checkpoint. Errori non autenticati, run invalidi/estranei o guasti DB non possono essere attribuiti a un run inesistente: risposta/log dichiarano `diagnosticPersisted:false`; un guasto di persistenza non maschera il codice originale.

Il completamento successivo conserva `lastDiagnostic` nel riepilogo; l’acquisizione riuscita azzera il codice di errore corrente. Un replay errato su run completato non ne trasforma stato o error corrente in errore: conserva solo la diagnostica del rifiuto. È una registrazione dell’ultimo rifiuto, non un ledger di tutti i tentativi.

Gli errori prima del parser JSON/raw sono intercettati anch’essi. Il controllo report/run è eseguito prima del parsing e ripetuto nella transazione: non sostituisce i lock autorevoli. Prezzi, cutoff, stock e classificazione FBM/FBA/annullamenti restano invariati.

La pagina `/marketplace/amazon`, elenco esecuzioni, mostra già `error`; nel riepilogo JSON della stessa esecuzione sarà disponibile `lastDiagnostic` con codice, fase e correlation ID. Non viene introdotto in questo hotfix il monitor delle 36 ore, che rimane la proposta separata.

## Rilancio e Make

**Non rilanciare ora soltanto per ottenere lo stesso 409 generico.** Il backend diagnostico è preparato e testato localmente, non è ancora in produzione. Prima occorre autorizzare push/merge/deploy. Se i metadati sicuri richiesti all’utente identificano già un errore di mapping/trasporto, correggere quello specifico; non cambiare quantità, identità o compressione per tentativi.

Dopo il deploy, con configurazione ancora dry run ON, Make OFF e nessun’altra esecuzione/retry in corso, un nuovo Run once autorizzato potrà riprendere il run pending e lo stesso report 213175020763. **Non serve chiuderlo o alterarlo nel DB**. Lo stato confermato rende il recupero possibile; non garantisce che il documento sia accettato. Se fallisce, il nuovo codice dirà il controllo applicativo esatto e verrà registrato, quando possibile, senza disattivare la riservatezza.

Non riprendere il solo vecchio modulo di download/upload da una incomplete execution con URL firmato scaduto. Riparti da import-window perché getReportDocument acquisisca un URL fresco. Dopo aver gestito privatamente i vecchi retry/incompleti, la guida [recupero senza Retry](CORREZIONE-RECUPERO-SENZA-RETRY-2026-11-06.md) consente modifiche manuali senza reinserire le 36 chiavi: tutti i 61 gestori Retry rimossi, Keep data confidential Yes, Store incomplete executions No, Process data in order Yes raccomandato.
